# 规则变更排查 SOP

## 适用场景
- 线上出现误杀、漏放、客诉，需要判断是否由规则变更引起；
- 业务方要求调整阈值、名单、优先级或灰度范围；
- 规则发布前需要产出可审批的材料。

## 执行步骤

1. **确认现象与时间窗**
   - 明确指标：命中率、误杀率、漏放率、通过率、客诉量；
   - 锁定时间窗，与规则变更发布时间对齐（精确到分钟）；
   - 记录数据口径（分母是申请量还是决策量）。

2. **拉取规则现状**
   - 调用 `rule_get` 获取当前规则 DSL、版本号、生效时间、灰度批次；
   - 确认规则依赖的特征是否近期变更（特征口径变化常伪装成规则问题）。

3. **定位差异**
   - 调用 `rule_diff` 对比变更前后版本，逐条列出条件、阈值、动作的差异；
   - 对每条差异标注影响面：影响的客群、交易类型、渠道。

4. **特征侧验证**
   - 调用 `feature_query` 抽查命中样本的特征分布；
   - 检查是否存在空值、默认值、分箱边界、特征延迟。

5. **回归与效果对比**
   - 调用 `rule_backtest` 在历史样本上回放；
   - 对比变更前后：命中量、误杀量、漏放量、金额影响；
   - 若样本量不足，明确说明置信度不足，不要给确定性结论。

6. **形成结论与建议**
   - 结论必须区分「已证实」「推测」「待验证」；
   - 建议给出最小变更方案与回滚方案；
   - 高风险动作（发布、灰度）必须走人工审批。

## 输出要求
- 报告写入 `/reports/rule_review_<时间戳>.md`；
- 规则 diff 写入 `/workspace/rule_diff_<时间戳>.md`；
- 审批材料写入 `/reports/approval_<时间戳>.md`，包含变更内容、影响评估、回滚方案、验证证据。

## 禁止事项
- 不得在未做回归测试的情况下建议直接全量发布；
- 不得伪造指标或样本量；
- 不得绕过审批直接调用发布接口。
